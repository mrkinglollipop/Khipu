## Received-context evidence

One actual Codex scenario ran, using `gpt-6-luna`, low effort, for both parent
and child. No second model run was used to repair the reader. The raw native
rollouts are private, outside Git:

```text

  rollout-2026-10-20T10-33-55-01a159bb-ae1b-7db3-b4c2-d2bb0c104ad0.jsonl
  rollout-2026-10-20T10-34-02-01a159bb-cdde-7b43-ab14-e6e8c25d8d88.jsonl
```

The parent contains the random hook sentinel in received developer context.
The child contains the known `probe.txt` contents in a native
`custom_tool_call_output`, followed by its final model answer. Before the
child's first tool call, a native developer message contains:

```text
Standing rules:
1. SYNTHETIC-ROUTING-OPENING synthetic rule SYNTHETIC-ROUTING-END
```

That developer message is stamped `hooks.additional_context`. It comes from
the production SubagentStart entry point, which the production installer also
wires for Codex. The initial rig calibrated child briefs as user messages;
this CLI stores NEW_TASK content encrypted. The final reader instead
calibrates the known native tool-result input without decrypting anything.

The original scenario ran before the final reader, run-metadata and matcher
refinements. Its successful process status and known calibrators were recorded
for offline replay from the completed run and known probe file. The raw
rollouts were not edited. Final launch wiring was not run again, to respect
the one-scenario-per-slice cost bound. Offline replay checks the final reader.
