Implementation
The existing timestamptz column already preserves microseconds. Only a blank
summary with a natural key different from the row holding its legacy key gets
a probed microsecond slot within its original UTC second. A source-key hash
chooses the starting slot; a transaction advisory lock serializes blank writers
in that second and probing handles truncated-hash collisions. The original
summary stays byte-for-byte blank, summary_kind stays verbatim_only, and raw
records blank_summary_original_ts when allocation changes the timestamp.

The source identity snapshot precedes allocation. The caller's shared payload
receives the allocated timestamp, so subsequent legs use the hub's actual key.
The legacy file writer still cannot store an empty summary: the existing file
leg skip remains conditional on hub evidence read-back. No file line is minted
under a different key. episode_sources reads the allocated legacy key from the
inserted row; forget reaches it through that key and its immutable natural key.
No schema migration, new store, fact writer, setting, command, gate or cooldown
change is needed. The added reader carries the existing writer-fence annotation;
the existing provenance writer and capture-store inventories are unchanged.

Faithful blank replays with an exact immutable source payload hash can match even
old captures with window_id but no part. That keeps replay stable if the first
legacy-key holder later gains a summary. Archive proofs require the recorded
original timestamp and exact natural fields when the allocated timestamp differs;
a coincident second alone is insufficient. Nonblank conflicts and blank captures
without a natural key retain their refusal path. Blank siblings use timestamp
allocation rather than adding a '(part ...)' placeholder to an empty summary.

rc=65 findings
Blank-summary verbatim_only payloads pass load_payload. EX_DATAERR also covers
invalid JSON, missing/invalid summary type or marker, and invalid timestamps.
Legacy-only mode really cannot persist an empty-summary payload. In hub/dual
mode, however, a collision can enqueue an outbox copy and then the legacy writer
can return 65 for the same blank capture, keeping the native job as well.
Those are two delivery copies of one capture, not independent episodes.
A successful hub write can also return 65 when evidence read-back is unconfirmed.

The specified M1 held job was inspected read-only, without printing its text.
Its outer timestamp is 2026-11-05T17:07:48Z; the checkpoint has a blank summary,
summary_kind=verbatim_only, one open loop, no regex verbatim, and no extracted
deliverables. The retry metadata says attempts=5, disposition=held,
last_error='capture rc=65', last_attempt_at=2026-11-05T18:22:25.846607+00:00.
The checkpoint intentionally lacks delivery identity: session_capture.drain adds
identity from the outer native job when retrying. Generic metadata cannot prove
which historical branch produced 65. This payload shape independently reproduces
the old false-unconfirmed result on a healthy hub: read-back only accepted verbatim.

The fix confirms the structured extraction on the live row's raw when no verbatim
exists, inside the same transaction before commit. Missing evidence still refuses
acknowledgement. held_without_summary no longer treats summary shape plus generic
rc=65 as proof of permanent unsavability; the false doctor words are removed and
these jobs follow the existing held-job recovery/red rule.
