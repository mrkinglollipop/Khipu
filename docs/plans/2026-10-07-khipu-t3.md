## Why Khipu matters more in T3

T3 Code (pingdotgg/t3code, the "v2" orchestration in the Nightly builds) lets one thread switch provider
(Claude, Codex, Cursor, Grok, OpenCode, Pi) and account mid-conversation. Each switch starts a new native
session and hands over a byte-budgeted selection of raw text. Reasoning, diffs, todos, tool and MCP results
are dropped from the hand-over. T3 keeps the full history in its own database and gives every agent a
`t3_thread_read` tool to fetch it, so within one thread nothing is lost for good, only not delivered.

What only Khipu can add: the *meaning* (decisions, preferences, open commitments, what superseded what),
continuity across T3 threads and across harnesses outside T3, and delivery without the agent having to ask.
That is the thing to build toward. "T3 loses context" alone is not the pitch.

## What T3 does (source facts)

Read from T3 commit `9f48092e` (2026-10-07, main) and the installed app, T3 Code (Nightly)
0.0.46-nightly.20261007.2787. Paths are under `apps/server/src/orchestration-v2/` unless noted. To re-check,
clone `https://github.com/pingdotgg/t3code` and check out that commit.

- **Switch decision.** A different driver, or an instance with a different continuation key, gets
  `create_with_handoff` (`ProviderSessionTransitionPolicy.ts:42-53`). The old live session is released
  (`ProviderSwitchService.ts:186-196`); its native transcript stays on disk. Not what happened on this Mac
  2026-10-07 (Claude main to the Claude second account): the old Claude process kept running after the
  switch and stopped about 30 minutes after its last turn, at the idle release (see slice B).
- **Claude accounts are separate homes.** Each Claude instance maps `homePath` to `CLAUDE_CONFIG_DIR`
  (`provider/Drivers/ClaudeHome.ts:36-54`); T3 creates and copies nothing into it. Different homes mean
  different continuation keys, so Claude to Claude-second-account is a new session plus a hand-over, not a
  resume. Codex accounts that share a `CODEX_HOME` resume the same native thread instead
  (`Orchestrator.ts:5155-5172`).
- **Hand-over content.** `ContextHandoffBudget.ts:140-170` keeps user text, assistant text, command input
  with exit code and output, errors, interrupt results, `proposed_plan` markdown, and changed file *names*.
  Dropped: reasoning, todos, diffs, searches, MCP and dynamic tool calls, subagent results, older attachments.
  Budget defaults to 16,000 bytes, `T3CODE_CONTEXT_HANDOFF_TOKEN_CAP` clamps 1,024 to 64,000
  (`:14-19, 107-138`). Order: last user message, last assistant message, first user message, then newest to
  oldest; an item that does not fit is omitted whole (`:256-261`).
- **Hand-over delivery.** Codex gets real history items through `thread/inject_items`
  (`CodexAdapterV2.ts:6507-6514`). Every other provider gets it prepended to the user's message as
  `${context}\n\nUser message:\n${userText}` (`ProviderTurnStartService.ts:1174-1186`). The context opens with
  `Context handoff (<strategy>):` (`ContextHandoffDelivery.ts:40`), then
  `Provider context handoff. Thread: <threadId>. Covered app runs: a-b.` (`ContextHandoffBudget.ts:272-278`),
  then items as `[Historical <role>; <kind>; thread=…; run=…; item=…; provider-thread=…; status=…]`
  (`:183-185`). It appears on the first turn after a switch, a fork, or a missed-items retry.
  Seen on this Mac 2026-10-07 (Claude to the Claude second account, strategy `full_thread_summary`): after the
  `Thread:` line come `Source item range: …`, `Recover omitted history using t3_thread_read(…)…` and
  `Selected 11 intact items; omitted 57 items. …` lines, then the items; the message ends with
  `\n\nUser message:\n` and the typed text. Khipu's per-prompt recall on that message put a raw-memories note
  headed `## Thread …` first.
- **Switching back** resumes the original provider thread with a `delta_since_target_last_seen` hand-over of
  only the runs it missed (`Orchestrator.ts:5721-5736`).
- **Session release.** Claude: SDK `Query.close()` ends stdin, sends SIGTERM after 2 s, SIGKILL about 5 s later
  (`ClaudeAdapterV2.ts:710, 7783-7828`; Agent SDK 0.3.276 `ProcessTransport.close()`). Idle release after 30 min
  takes the same path. Codex: the app-server is not killed on a switch; the thread gets `thread/unsubscribe`
  (`CodexAdapterV2.ts:6601-6604`).
- **Thread identity.** One T3 `ThreadId` has many `ProviderThread` rows, each with its own native session id
  (`packages/contracts/src/orchestrationV2.ts:870-906`). No environment variable or argument tells the agent
  its T3 thread. The local database `~/.t3/userdata/statev2.sqlite` maps them:
  `select thread_id from orchestration_v2_projection_provider_threads
   where json_extract(payload_json,'$.nativeThreadRef.nativeId') = :claude_session_id` (checked on one row).
- **T3's own MCP server** (`t3-code`, HTTP on localhost with a bearer token) is injected into every agent and
  exposes `t3_thread_list` (with `currentThreadId`), `t3_thread_read`, `t3_thread_search` and more
  (`apps/server/src/mcp/toolkits/*/tools.ts`, `packages/contracts/src/orchestratorMcp.ts:335-351`).
- **Settings loading.** Claude runs with `--setting-sources=user,project,local` (seen in the live process on
  this Mac) from its home; Cursor's SDK is given `settingSources` project, user, team, mdm, plugins
  (`CursorAdapterV2.ts:297-303`); Codex on this Mac runs in direct mode on the real `~/.codex`
  (`~/.t3/caches/codex.json`), and managed extra Codex homes symlink `config.toml` and `hooks.json` from it
  (`CodexHomeLayout.ts:373-408`). T3 also runs helper Claude sessions in temp folders named
  `t3code-claude-title-*`.

## Findings on this Mac (verified 2026-10-07)

- Main Claude account (`~/.claude`): Khipu's SessionStart, per-prompt recall and Stop hooks all fired in a
  T3 session, and the Khipu MCP server ran inside it (checked under the 0.0.45 build, before v2).
- Second Claude account (`~/.claude-t3-second`): no `settings.json`, no `mcpServers`. Three real sessions
  there (church-harness project) ran with no Khipu, no global instructions, no hooks.
- Khipu writes `settings.json` with an atomic `os.replace` (`packages/cli/khipu/integrations.py:389-393`).
  On a symlinked `settings.json` that replaces the link with a plain file and silently un-shares the setup.
- Khipu only knows `~/.claude` (`integrations.py:402-407`); `CLAUDE_CONFIG_DIR` appears nowhere in the CLI.
  `infer_harness` (`session_capture.py:212-230`) labels a session `claude_code` only if its transcript path
  contains `/.claude/` or `CLAUDE_PROJECT_DIR` is set, so second-home sessions may come out `unknown`.
- The recall hook passes the prompt through raw (`recall_prompt.py:1121, 1318`); embedding keeps the first
  8,000 characters (`embed.py:67`) and the lexical leg the first 8 content tokens (`search_text.py:53, 70`).
  After a switch, recall would search T3's hand-over header instead of what the user typed.

## Decisions

1. The second T3 Claude account gets *everything* from `~/.claude` on this Mac, not just Khipu (slice 0).
   That is a local setup step, not a Khipu feature.
2. The Khipu feature is narrower and ships for everyone: Khipu installs into every Claude home it can find,
   T3's included (slice A).
3. Khipu never writes to T3's database or config. Reading them is allowed and must degrade quietly when the
   files are missing or their shape changes.
4. Grok, OpenCode and Pi through T3 are out of scope here (Khipu has no integration for them anywhere).

## Slice A: Khipu in every Claude home, clean prompts

Inspect `packages/cli/khipu/integrations.py`, `session_capture.py`, `recall_prompt.py` and the desktop
Integrations / Components screens before writing anything.

1. **Find the homes.** `~/.claude` always; `CLAUDE_CONFIG_DIR` when set; every Claude instance in
   `~/.t3/userdata/settings.json` (empty `homePath` means `~/.claude`). Read-only, tolerant of a missing file

2. **Install, status and uninstall per home**: hooks in `settings.json`, the `khipu` entry in `.claude.json`

4. **Strip T3's hand-over** in both the recall hook and capture's `_clean_user_text`: when the text starts

5. **Skip T3 helper sessions**: a cwd containing `t3code-claude-title-` means no recall and no capture,
   exit 0 quietly.
6. **Show it**: doctor and the desktop Integrations screen list one row per Claude home, e.g.
   "Claude Code (T3 second account)". UI needs an approved mock first, in `docs/mockups/` like the other
   mocks. If the mock is not approved, stop after the CLI work and ask.

per change. Desktop changes ship in the next release; no release cut for this slice alone.

## Slice B: prove what a switch does

Matt drives the T3 UI; the agent reads the evidence. In a scratch project: three turns on Claude (main
account), switch to Codex for two turns, switch to the Claude second account for one turn, switch back to
Claude main for one turn.

Check after each switch:
- The hand-over text actually delivered (the Claude transcript's user message; rows in
  `orchestration_v2_projection_context_handoffs`).
- Whether Khipu captured the outgoing session's last turns (`khipu_search` with `session_id` set to the
  native id prefix). Captures normally land every 5 turns or 20 minutes or at SessionEnd; T3 gives Claude
  about 2 s before SIGTERM, Khipu's SessionEnd hook allows 20 s. Unknown until observed.
- Whether Codex fires its hooks when a thread is unsubscribed rather than ended.

First observation, 2026-10-07, one Claude main to Claude second account switch in a real thread (not the
scratch run above): the outgoing session's last Stop logged `not due (turns=3, elapsed=753s)`, so its last
three turns were not captured at the switch (21:07 UTC). Its process (`7ad9bf1d…`) was still running at 21:10
and 21:30. At 21:31:51, about 30 minutes after its last turn (21:01:50), it ended; the SessionEnd hook queued a
capture and the next drain stored it (episode 16485, mock turn included). So on this path nothing was
lost, only delayed by up to the idle timeout. The scratch run still has to cover a forced release and Codex.

If turns are lost: add a backstop that captures transcripts whose newest turn is newer than their newest
capture. Read the existing capture cadence and dead-letter code first and extend it rather than adding a
parallel path. Never start the nightly midday to test it.

## Slice C: one T3 thread, one conversation

1. **Map sessions to threads** with the read-only query above (open the database read-only with a short
   timeout; the file is in WAL mode). Stamp each capture from a T3 session with its T3 thread id and a
   `via: t3` marker. Check the mapping on more than one row first.
2. **Filter**: `khipu_search` can filter by T3 thread and by `via`.
3. **Switch-aware recall**: when the prompt carries a hand-over header, take the thread id from
   `Thread: <id>` and put that thread's decisions and open commitments (from its earlier sessions, any
   provider) ahead of the usual top 3, within the recall time budget. Measure latency against the current
   per-prompt budget before and after.
