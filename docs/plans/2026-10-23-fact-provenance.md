## 1. The problem in one paragraph

Capture deduplicates. A second episode that restates an open commitment does not get its own row: it overwrites `commitments.latest_text`, unions its PR numbers into `prs` and `pr_check.refs`, and bumps `seen_count` (`commitments.py:1158-1191`). A repeated decision or deliverable is skipped outright (`decisions.py:323`, `deliverables.py:66`), and so is an owner supersession whose words repeat one already on file (`decisions.create_decision`). Nothing records who supplied which value. Forget then has to act on the fact row by its anchor episode alone (`forget.py:213-237`): it closes, retracts or deletes facts that a kept episode also supports, and it never touches wording a non-anchor episode wrote. The attempt added a support table but kept the question "which episode supplied this value?" open at forget and cleanup time, answering it by re-reading raw captures with a second set of matching rules. Those rules disagreed with capture's (kind, mutable owner), so forgotten wording stayed readable in some schedules and live wording was deleted in others (third review, P1 #2). Every later fix patched one disagreement and exposed another.

## 2. Invariants (each is a test)

I1. **Forgotten wording is never readable.** After `forget_episode(E)` commits, no reader returns a value whose only claimants (section 3) are forgotten episodes. Readers: hub `list_owed`, `list_decisions`, `recent_deliverables`, search, get, briefs, the MCP tools, gateway mode; and each replica's readers once its next `pull_changes()` returns ok. Test: for every claim value `v` held by E, assert `v` is absent from every reader's output unless a live episode or the owner also claims exactly `v`.

I2. **Live supported wording is never deleted.** If a live episode or the owner holds a claim on fact F, then no forget, backfill or cleanup retires F, and each projected field of F is one of its live claims' values (by the projection rules in 3.2). Test: generated schedules over captures A/B/C with mixed kinds and owners, owner reassign, an old-code writer (refused, 5.2), and forgets of every subset. Assert after each commit.

I3. **Forget never overwrites owner edits.** Owner fields (3.3) are byte-identical before and after any forget, backfill or cleanup. The one exception is the retirement status of a fact left with no live or owner claim, and even then the owner fields stay on the row. Owner claims are removed only by the owner. Test: snapshot owner fields, forget, compare.

I4. **No capture silently loses a fact.** Every capture job ends in exactly one of three states: committed, with a claim for every fact item it derived; still queued in the outbox, not buried, with a named deferral reason; or committed with a `fact_gaps` row that doctor reports and the nightly re-runs. Test: inject `DeadlockDetected`, `SerializationFailure`, `LockNotAvailable`, `QueryCanceled` (statement timeout), a gate refusal and a plain bug into each fact step. Assert one of the three states each time, and assert the outbox job was never acknowledged without one.

I5. **No owner write is applied twice or to the wrong hub.** A queued owner write applies at most once, and only to the hub whose identity it was bound to when it was queued. An entry with no binding is never applied until the owner binds it explicitly. This is a separate change (section 7). It is listed here because the same review cycle broke it.

I6. **Wording changes only through the projector** (the mechanism behind I1 and I2). In any transaction that changes a fact's wording columns, the projector must have recorded that fact in `fact_changes` in the same transaction, or the commit fails. This holds whatever code version is writing. Test: a direct SQL `UPDATE commitments SET latest_text = ...`, an old-code dedup and an old-code forget each fail at COMMIT.

## 3. The model: claims, one projector

**Chosen: every stored wording value has exactly one claimant, recorded when it is written.** The claimant is either a capture episode or the owner, and the record is a row in `fact_claims`. A fact's visible wording is a pure function of its live claims, computed by one function, `khipu/provenance.py: project(cur, kind, fact_id)`. Capture dedup, forget, legacy backfill and any future cleanup change wording only by adding or deleting claims and then calling `project()`. No code path reads raw captures to work out after the fact who said what. Dedup keeps its current rules (exact hash, paraphrase match, owner separation): they decide only *which fact* a new claim attaches to.

**Rejected: a support set beside the fact row, re-derived from raw on forget and cleanup (the attempt).** It needs two equivalence rules, the writer's dedup and the forget/cleanup witness classifier, and they must agree forever. They already disagreed on kind, on an owner that `reassign` can change, and on support rows that existed but were ignored. The two rules lived in different modules, so the drift was invisible until a review hit it.

**Also rejected: no cross-episode dedup in storage** (one row per occurrence, grouped at read time). Forget would become a plain cascade, but every reader, the close rules, owner edits (which would target a group, not a row), replica schema and paging would all change. That is a much bigger change for the same invariants.

### 3.1 Tables (one migration, 0047)

- `fact_claims(kind, fact_id, field, value, claimant, episode_id NULL, xid xid8 DEFAULT pg_current_xact_id(), created_at)`. `claimant` is one of `episode`, `owner` or `legacy_unproven`. PostgreSQL refuses a primary key on expressions, so the claim's key is a unique index on `(kind, fact_id, field, md5(value), coalesce(episode_id, 0), claimant)` (the `ON CONFLICT` target), with a surrogate `id` primary key; a replayed capture writes nothing new. `field` is one of: commitment `text`, `restatement`, `pr`, `pr_ref`; decision `text`, `rationale`, `evidence`; deliverable `title`, `support`.
- `fact_changes(seq bigserial, xid xid8 DEFAULT pg_current_xact_id(), kind, fact_id, via, at)`. `project()` writes `via = 'project'` rows, the only ones the commit gate (I6) accepts. A plain trigger on `decisions` and `deliverables` writes a `via = 'row'` row for any other insert, update or delete (owner supersede, retract, confirm), so the replica stream (section 6) sees lifecycle changes too. `at` drives the 30-day prune; `fact_changes_floor(pruned_through xid8)` records how far it has removed rows.
- `fact_gaps(episode_id, step, error, at, resolved_at, source_id, resolution, attempts)`. Used for I4. `source_id` names the merged capture (its payload hash) for a merge step's gap; `resolution` and `attempts` are the nightly replay's (Astra fix #6).
- `provenance_projects(project, backfilled_at)`. Legacy witness progress (section 4).
- Triggers, all `DEFERRABLE INITIALLY DEFERRED` constraint triggers with `WHEN (OLD.col IS DISTINCT FROM NEW.col)`:
  - Fact-table gate (I6). Fires on INSERT into `commitments`, `decisions` or `deliverables`, and on UPDATE of a wording or anchor column: commitments `text`, `latest_text`, `prs`, `pr_check->'refs'`, `opened_episode`; decisions `text`, `rationale`, `evidence`, `episode_id`; deliverables `title`, `episode_id`. It requires a `fact_changes` row for `(kind, NEW.id)` with `xid = pg_current_xact_id()`.
  - Forget gate. Fires on UPDATE of `episodes.deleted_at`. It requires that no `fact_claims` row names that episode.
  - Claim gate. An immediate (not deferred) `BEFORE INSERT` trigger on `fact_claims`: an episode claim takes `FOR SHARE` on the episode row, before any fact lock (the lock order in 3.4), and refuses a deleted or missing one. This serialises it with forget's `FOR UPDATE` (`forget.py:116`). It refuses with `check_violation`, not `08K01`: an old writer never inserts claims, so this refusal is always a new writer's bug and must not read as "upgrade it" or as hub-away.
  - Writer gate (Astra fix #5). An exact repeat of facts already on file changes no fact column, so the fact-table gate never fires for it and an old writer would commit the episode with no claims. A deferred trigger on INSERT into `episodes`, and on an UPDATE of `raw` that adds a `merged_from` entry, fires when the capture carries fact items (non-empty `open_loops`, `decisions` or `deliverables`). It requires the transaction-local setting `khipu.fact_writer = on`, which `provenance.declare_writer` sets inside each fact step that records claims and again when a fact gap is recorded. An old writer never sets it.
  - Supersede gate (Astra fix #5). A deferred trigger on UPDATE of `decisions.superseded_by` with source `manual` or `agent` requires a `via = 'project'` change for the replacement in the same transaction, i.e. the owner claim of 3.3. An old supersede that reuses an existing decision records none.
  - The fact-table, forget, writer and supersede gates refuse with SQLSTATE `08K01` and the message "khipu: this writer predates fact provenance; upgrade it". The reason is in 5.2.

### 3.2 Projection rules (`project()`, the only writer of these columns)

| Fact | Field | Projected value |
|---|---|---|
| commitment | `opened_episode` | the earliest live `text` or `restatement` claimant. A forgotten anchor is kept only when the fact retires |
| commitment | `text` | the anchor's own claim value |
| commitment | `latest_text` | the newest live `restatement` value that differs from `text`, else NULL |
| commitment | `prs`, `pr_check.refs` | the union of live `pr` / `pr_ref` claims and owner claims; `prs` sorted, `refs` in the order each was first claimed (the order the pre-provenance writer appended them). A `legacy_unproven` PR value that no live or owner claim also holds sets `pr_check.needs_owner`, and close rules then never auto-close the fact (the owner closes it; phase 3, see 8) |
| decision | `episode_id`, `text` | the earliest live claimant and its own words. An owner claim with no live episode leaves `episode_id` NULL |
| decision | `rationale`, `evidence` | the anchor's claim, if it has one, else NULL |
| deliverable | `episode_id`, `title` | the earliest live claimant and its own title |
| any | retirement | no live and no owner claim: close (`forgotten`), retract (`forgotten`) or delete exactly as `forget.py:213-237` does today, with the anchor left on the forgotten episode so the existing reader fences keep hiding it |

When `text` or `latest_text` changes, `project()` also deletes the fact's `memory_embeddings` row (the nightly re-embeds it). `content_hash` is identity, not wording, and is never recomputed. This removes the owner-separated hash collision class (first review #6).

### 3.3 Owner fields (never written by forget, backfill or cleanup)

Commitments: `status` (except retirement), `owner`, `owner_label`, the reassign lineage columns, `due_after`, snooze, `linked_ids`, `reopened_rule_keys`, the `pr_check` keys other than `refs` and `needs_owner`. Decisions: supersede and retract state, `decision_links`, confirm and reject. Owner-authored wording is an `owner` claim. That covers `create_decision`, including when it deduplicates into an existing row, a manual or agent `supersede` (its replacement gets an owner claim on its text, whether it was created or chosen by id, as 0047 records for a legacy owner link; Astra fix #4), and any future owner text edit. On main today no owner API edits commitment, decision or deliverable wording.

### 3.4 Locks and errors

- There is no global mutex. The attempt's advisory lock caused the second review's deadlock class and the third review's statement-timeout loss.
- Lock order for every writer: episode row(s), then fact rows in `(kind, id)` order.
- Deliverable creation (fourth Astra review #4). A row that does not exist yet cannot be locked, so a capture or gap replay first takes a transaction-level lock on each deliverable dedup identity it carries (`pg_advisory_xact_lock` on the identity's hash: project, kind, path, url, and the title for an item with neither), in sorted order, after its episode lock and before any fact row. Two transactions carrying the same deliverable (two captures, or replays of two different gap groups) then serialize: the second finds the first's row and adds its claim to it. A different identity never waits; this is not a global lock.
- Forget: `FOR UPDATE` on E, select E's claimed facts, lock them in order, delete E's claims, `project()` each, then the existing tombstone steps.
- A restatement keeps the PR refs the current `latest_text` names, claimed by whoever supplied that wording. It runs after the fact lock, so it never re-inserts a claim already on file (whose claim gate would lock that episode after the fact, the reverse of forget's order: seventh Astra review #2); a missing one first takes that episode `FOR SHARE NOWAIT`, so a forget holding it makes the capture defer (`LockNotAvailable`) instead of deadlocking.
- Capture dedup: lock the target with `FOR UPDATE ... WHERE status = 'open'` and re-check. If the target has retired in the meantime, take the insert path. That includes a commitment insert that lost its `ON CONFLICT` to a concurrent capture whose row then closed before it could be locked: the insert is retried (3 attempts in all), then the capture defers as `FactStepDeferred` (Astra fix #3).
- These four errors in a fact step make the whole capture transaction roll back as `FactStepDeferred`, which the outbox retries and never buries (like `ClaimDeferred`, `outbox.py:495`): `DeadlockDetected`, `SerializationFailure`, `LockNotAvailable` and `QueryCanceled`. So does SQLSTATE `08K01`, after a readiness refresh.
- Any other fact-step error keeps today's savepoint rollback (`capture.py:1207-1270`, merge path `:669-750`), and also writes a `fact_gaps` row in the same transaction.
- Gap replay (Astra fix #6): `provenance.replay_gaps`, in the nightly's close-rules step after the backfill. Per open gap group (episode, step, merged capture), in one transaction: `FOR SHARE` on the episode, then the group's open gap rows `FOR UPDATE SKIP LOCKED` (a group another runner holds or has resolved is skipped, so two Macs' nightlies never both run it; Astra 2 fix #3), re-run that step's calls on the capture (the episode's raw, or the `merged_from` payload `source_id` names), mark the gaps resolved. A forgotten episode or source is resolved as `forgotten` and never replayed. A failed replay rolls back and leaves the gap open with its error and attempt count, for doctor and the next night. Each night takes at most 200 groups, fewest attempts first and then oldest, so groups that keep failing fall behind ones never tried and cannot starve them (Astra 2 fix #4). A replayed step is followed, in the same transaction and in capture's order, by the steps that read what it writes and so ran against its missing rows: `decisions` by `decision detection` and `close rules`, `commitments` by `close rules` (`provenance.DEPENDENT_STEPS`; the merge path's `merge ` steps alike). Each is idempotent (Astra 3 fix #4).
- File recovery (Astra 2 fix #5). `mirror.sync_recent_episodes` and `mirror.reconcile_memory_root` import a missing file line with capture's own fact steps (`capture.run_fact_steps`, the block `write_pg` runs) when the hub has 0047 and the line carries fact items, so the writer gate admits it with its claims or a fact gap. A line whose fact step defers is rolled back alone and queued in the outbox with its owner unknown (`origin` NULL, as a direct recovery leaves it: a synced file can hold another machine's captures), never the recovering caller's (Astra 3 fix #3); the rest of the batch commits. A held legacy key `(ts, md5(summary))` is not proof that a line's facts arrived: a fact-bearing line whose key the hub holds (or that collides on insert) is compared, item by item, with the open loops, decisions, decision details, deliverables and closed loops (a line carrying only closed loops counts as fact-bearing for both entry points, fifth Astra review #4) (every input the fact steps derive facts from; decision details carry a decision's rationale and reversal evidence, fourth Astra review #3) of every episode at that key (its raw and the captures merged into it). An equal replay is skipped; a line carrying an item none of them holds is queued in the outbox with its owner unknown, where its drain either lands its facts through capture's dedup or stays queued as an `evidence_conflict` (never buried; outbox status and doctor count it) (Astra 3 fix #2). `mirror.mirror_episode` is unchanged: its refusal is queued by `mirror_after_capture`.

## 4. Legacy data (unknown provenance: never guessed)

Migration 0047 attributes a value only when the code proves who wrote it.

- **Proven by the writer inventory.** Each of these columns has exactly one writer, the insert by the anchor episode: commitment `text`, `prs` equal to `parse_prs(text)`, decision `text`/`rationale`/`evidence`, deliverable `title`. A commitment whose `prs` is NULL (never parsed, from before 0034) keeps NULL through the migration (the projection keeps NULL while the fact has no `pr` claim), unless its text contains no `pr` or `pull` at all, which no reading can turn into a PR, and is settled as `{}`. Its one writer, `close_rules.backfill_prs`, then records `parse_prs(text)` (the exact parser, not the stricter SQL reading) as claims of the text's claimant and projects; a capture that dedups into such a row claims those numbers first (built in phase 3; phase 2 had the migration prove them with the SQL reading, which can miss a number). Each gets an `episode` claim for its anchor. A decision that is the `new_id` of an owner-made supersede link gets an `owner` claim. `tests/test_episode_write_gate_inventory.py` (or a sibling) pins the single-writer list, so a new writer breaks the build.
- **Unproven.** Commitment `latest_text`, any `prs` or `pr_check.refs` beyond what `text` yields, and any value the inventory cannot explain become `legacy_unproven` claims. `project()` never shows them, so the migration's own projection sets `latest_text` to NULL and turns on `needs_owner` where it applies. The values stay in the hub-only claims table, on the same terms as a forgotten episode's raw, and are never sent to a replica.
- **Witness backfill** (`khipu provenance backfill`, nightly until `provenance_projects` is complete). For each project, it streams live episodes (keyset pages by id, so the nightly can commit between batches) selecting only the open loops, decisions and deliverables of `raw` and of `raw->'merged_from'[*].payload`, in batches of 500. For each item it computes the value the writer would have stored, by calling the writer's own value function (`_normalize_open_loop(...)["text"]`; `_redacted_value(str.strip())` with `normalize_text` for decisions; the deliverable dedup key). If that value exactly equals a stored or unproven value on a fact in the same scope (the episode's `project`; facts retired as forgotten excluded), and that episode does not already hold that value on a fact (it opened its own, such as an owner-separated twin, or a capture after 0047 claimed it), the episode gets an `episode` claim and the fact is re-projected. Commitment PR numbers and refs (`pr_requirement_labels` with the project's repository, so a plain "PR #41" ref is proven too) are claimed when the episode's words name a value already on the fact; this also clears `needs_owner`. Decisions match on the stored text byte for byte, not on `normalize_text`. Kind and current owner are never compared. Memory is bounded by the batch, not the project. This answers the third review's #5 and the second review's P3.
- **Before a project is backfilled,** forget runs that project's backfill first. It is the same function, streamed, under the same locks, so there is only one code path. Forget locks the episode, then its facts in `(kind, id)` order, then backfills (whose claim gate takes `FOR SHARE` on other episodes): two forgets that both run one project's first backfill can deadlock, and the refused one changed nothing. `forget_everywhere` retries a deadlock or serialization failure itself until a time budget is spent: 90 seconds from the first attempt (`forget.FORGET_RETRY_BUDGET_S`), with a short growing pause of at most a second. It is time-bounded, not a count of attempts (seventh Astra review #2: four attempts could be exhausted by a short run of restatements). The nightly runs the backfill inside its close-rules step, before `backfill_prs` and the rules.
- **Accepted limit.** A legacy restater whose words were later overwritten left no stored value, so it cannot be proven. If every provable claimant of such a fact is forgotten, the fact retires as it does on main today. Doctor counts these: retired legacy facts with `seen_count` greater than their proven claimants. No fuzzy matching is used to rescue them.

Why exact equality is safe for I1: if a live episode's capture produces exactly `v`, then `v` is not wording that only forgotten episodes hold.

## 5. Rollout on a live hub (enforced in code, not by deploy order)

### 5.1 Before the migration: new code on the old schema

New writers check for `fact_claims` with `to_regclass` at the start of each transaction and cache only a positive answer. That fixes the first review's #3. Without the table they behave exactly as main does. They always write claims and call `project()` when the table exists. A writer whose check went stale is caught by the gate (I6) at COMMIT, retried as `FactStepDeferred`, and its next attempt sees the table. That fixes the first review's #1, and the database enforces it, not code discipline.

### 5.2 Old-code writers after the migration

This covers other Macs' live slots, the gateway at `/opt/alzy/bin`, and anything still on main.

- **Old captures.** Every wording write fails the deferred gate at COMMIT, and that rolls back the whole transaction, savepoints included. The old fail-open steps cannot commit an episode without its claims. The error is class `08`, which old `hub_errors.unreachable_error` treats as "hub away" (`hub_errors.py:52`). The old outbox stops, keeps the job queued and never buries it (`outbox.py:514`). Captures land after that Mac upgrades. Phase 1 verifies this mapping against the pinned psycopg (stop condition).
- **Old forget.** It fails the forget gate, so nothing is tombstoned and the caller sees an error. Its local fence is published before the hub step (`forget.py:136`), so a refused old forget leaves a local tombstone with no hub tombstone. That is an existing split, and the same as an unreachable hub. The new forget heals it on retry.
- **Old owner writes.** Lifecycle writes (close, reopen, snooze, reassign, retract) touch no wording and keep working. An old supersede inserts a decision, or reuses an existing one, fails the gate, and is reported to the owner as refused or waiting, never as applied.
- **Old exact repeats** (Astra fix #5). An old capture whose facts are all already on file word for word writes no fact column but still meets the writer gate (3.1), so it is refused and queued like any other old capture. An old capture with no fact items at all still lands.

This fixes the second review's P2-3 and the third review's #2 old-binary cases by refusal, not by later repair.

### 5.3 The migration itself (0047, one file, one transaction)

- Number 0047. The runner refuses to run it if `schema_migrations` records 0045 or 0046 (a disposable hub from the attempt).
- It takes `ACCESS EXCLUSIVE` on `episodes`, `commitments`, `decisions` and `deliverables`, in writer lock order, before anything else. Writers in flight finish first, so the backfill sees them. Writers that arrive later wait, then meet the gate.
- In the same transaction it creates the tables, then the proven and unproven claims, then the initial projection with `fact_changes` rows, then the triggers. Because it is a single file there is no intermediate state like the attempt's 0045-only window (first review #7).
- Exhausting the lock retries (`migrate.py:333`) rolls the whole file back. Idle-in-transaction readers are the known cause (third review, 0046 section).
- Run it in a quiet window, after `khipu promote` on this Mac, the other Macs and the gateway (`merged-is-not-deployed`).
- **Rollback.** Code rollback after 0047 means every writer is refused. Undoing it is migration 0048, which drops the four triggers and keeps the tables; with section 6 it also sets `fact_copy_ready.state = 'indexing'` in the same transaction before dropping the identity triggers, so no replica keeps admitting copies against unenforced refusals. It is an owner-directed action through the agent, per `2026-10-16-owner-direction.md`, and needs no terminal.

### 5.4 Replicas written before this design

A replica written by earlier code has no stamp, so its readers show no fact row until its first copy passes the load rule (6.2). Its registry strings for forgets made on the hub match once the index pass has completed every tombstoned episode's forms (6.1); any it still holds that the hub lacks are listed for the owner (6.2), never sent automatically. A replica that still holds the branch's retired tables (`replica_fact_sources`, `replica_source_index`, `replica_fence_applied`, `replica_anchor_sources`) drops them at its first copy.

## 6. Replica: a copy of the hub's facts; refusals are matched only on the hub (proposed 2026-10-24, amended after the design review)

This replaces the replica rules at `f3ab8344` (fact change stream on the replica, rebuild rule with generations, wait rule with confirmations, `confirm_from_hub`, "Send N forgets"); their text is in git there. The first proposal (`28a469c0`) was reviewed in `jobs/2026-10-23/astra-prov-design/report.md`: architecture kept, 4 P1 and 3 P2 gaps (F1-F7) and one P3 (F8), all closed below. The re-review (`jobs/2026-10-23/astra-prov-design2/report.md`) kept the architecture and required six changes, N1-N6, each made below in its smallest form. Owner answers (2026-10-24, orchestrator recommendation under Matt's "proceed as you rec"): nothing sends refusals automatically; forget needs the hub, as on main; the rollout sweep runs only behind a database readiness barrier; a whole copy is skipped when the hub's facts have not changed, and a sustained-workload benchmark gates the build.

**Principle.** Every match of a refusal to an episode happens on the hub, in one transaction under the per-identity lock capture and merge already take (0030's `khipu-source:<identity>` advisory lock). The replica checks only that each string in its registry is a row on the hub, and copies the hub's facts whole.

### 6.1 Hub

- **One refusal table, one codec.** `forgotten_sources(identity)` (0030) holds every refusal. Keys and payload hashes stay bare hex, as 0030 stores and locks them; a legacy identity is `legacy:<ts>\x1f<md5(summary)>`. Bare episode ids are never hub refusals (F4). One function, `tombstones.hub_form(tag)`, maps a registry tag (`k:`, `h:`, `l:`, `tombstones.py:324-331`) to its hub form, and every sender and the load rule use it. The SQL legacy form in the triggers is pinned to it by test.
- **Database-taken identity locks (F3).** A `BEFORE INSERT` trigger on `forgotten_sources` and on the new `episode_identities` takes the identity's advisory lock before its check, as 0030's `khipu_refuse_forgotten` does for episodes (`0030_forgotten_sources.sql:110-123`). The insert and merge triggers on `episodes` and `episode_sources` take every identity's lock, refuse a forgotten one (legacy form included), and record each in `episode_identities` in the same transaction. Restricted, and refused with `check_violation`: any UPDATE or DELETE of `forgotten_sources` or `episode_identities`; a DELETE of an episode that has identity rows (the hub has no episode DELETE today; only the SQLite replica deletes); an episode insert or merge that announces no identities in `khipu.source_identities` (writers before 0030); and a refusal or carrier write from a transaction that is not READ COMMITTED (the trigger's post-lock check needs a fresh view; every hub writer is READ COMMITTED today). A statement-level `BEFORE TRUNCATE` trigger refuses TRUNCATE of `forgotten_sources`, `episode_identities`, `forgotten_at_cutover` and `fact_copy_ready`, and a DELETE of the `fact_copy_ready` row is refused (N6); bypassing triggers as superuser is outside the supported contract. An identity row is never removed: an episode keeps every identity it ever carried.
- **Identity additions serialize on the episode row (N5).** The insert triggers on `episode_sources` and `episode_identities` take the episode's row `FOR SHARE` after their identity locks, so no identity, a source-receipt-only one included (`capture_identity.py:121-143` inserts without the row lock today), can commit into an episode while a forget holds it `FOR UPDATE`.
- **Carrier gate.** A deferred constraint trigger on both tables refuses a commit that leaves a live episode recorded under a refused identity. With the locks above, two writers of the same identity cannot both be uncommitted: the second waits, then its check sees the first.
- **Identity index and readiness barrier (F2).** 0047 creates `episode_identities`, the triggers above, one row `fact_copy_ready(state, target_id, indexed_through)` with `state = 'indexing'` and `target_id` = the highest episode id at migration time, and the insert-only `forgotten_at_cutover(episode_id)`, filled in the same transaction with every episode then tombstoned: the frozen set of forgets the owner actually asked for before this design (N2). From then on every new write is indexed by the triggers. History is indexed by one streamed pass (`khipu provenance index`, in the nightly's close-rules step and on demand), in batches of 500 episode ids. Each batch is one transaction: compute every identity of each episode's raw and `merged_from` payloads with the registry's own functions (`tombstones._identity_values`, `_hub_identities`, the legacy form); take those identity locks sorted, then the batch's episodes `FOR UPDATE` in id order; insert the identity rows; for every episode of the batch in `forgotten_at_cutover`, insert all its identities into `forgotten_sources` (the hub's own past forgets, completed with every form). Membership in that frozen set is the only thing that makes the pass add a refusal: an episode the pass or `refuse()` tombstoned as a collateral carrier never has its other identities refused, whatever the batch order. Then tombstone, in the same transaction, every live episode now recorded under a refused identity (the pre-0030 duplicate sweep, owner answer 2); advance `indexed_through`. Indexing and tombstoning commit together, so the carrier gate passes per batch; an aborted batch (deadlock, crash) advances nothing and is redone from the committed cursor. A trigger on `fact_copy_ready` refuses `state = 'ready'` unless `indexed_through >= target_id`. Until the row exists and says `ready`, no replica admits a copy (6.2). `khipu provenance index --dry-run` counts what the sweep would tombstone, from the same frozen set; that count is shown with the migration go (phase 5).
- **The refusal transaction**, `provenance.refuse(cur, identities, deadline)`. One READ COMMITTED transaction, all or nothing: take the identity locks sorted; insert the identities (`ON CONFLICT DO NOTHING`); select the live episodes `episode_identities` records under them; lock those `FOR UPDATE` in id order; on each, delete its claims, `project()` the affected facts and tombstone it (3.4); commit. `forget_episode(E)` is `refuse()` over every identity E carries, with one addition (N5): after taking the identity locks it locks E `FOR UPDATE` and re-reads E's full identity set under that lock. If the set grew, it rolls back, publishes the grown set to the local registry (as `forget.py:231-241` does today) and retries from a fresh sorted set within the same deadline; it never takes an extra identity lock in place. A forget whose set keeps growing until the deadline reports not done.
- **Carrier closure (F6).** The refusal set is exactly what was asked: for a forget of episode E, every identity E carries; for an owner send (6.2), the strings sent. Carriers are tombstoned; their other identities are not refused. So a merged episode F that shares identity H with E is tombstoned with E, and F's own capture under another identity G is not refused: a later upload of G lands live with its own claims. The inner step is a new helper that publishes nothing; the existing `publish_hub_forget` call (`forget.py:298`) goes, which removes the F6 retry loop.
- **Lock order.** Identity locks (sorted), episode rows (id order), fact rows (3.4). A merge locks its target before its trigger takes identity locks, so a merge and a refusal can deadlock; the database aborts one. Capture's whole-transaction boundary (`capture.py:1418-1424`, today only the old-writer refusal) maps `40P01`, `40001`, `55P03` and `57014` raised anywhere in the transaction, merge target lock and COMMIT included, to `FactStepDeferred`, which the outbox never buries (`outbox.py:538`). `refuse()` retries within its deadline (6.4).
- **Change token.** A statement-level trigger on INSERT, UPDATE, DELETE and TRUNCATE of every table the copy reads (commitments, decisions, decision links, deliverables, fact vectors in `memory_embeddings`, `forgotten_sources`, and `episodes.deleted_at`) writes one `fact_changes` row (`via = 'copy'`), so its `xid` marks the change. The nightly prune deletes only an `xid` prefix (rows below the xid of the oldest row it keeps), so "no row older than X was removed" can be read from `min(xid)`. `fact_changes_floor` is not needed.
- **Hub incarnation (N3).** `(system_identifier, timeline_id, database oid)` from `pg_control_system()`, `pg_control_checkpoint()` and `pg_database` for `current_database()`; the control functions are cluster-wide, so the oid tells two databases of one cluster apart. A new cluster changes the first, a point-in-time restore the second, and a logical restore (`pg_restore` into a new database) or a clone (`CREATE DATABASE ... TEMPLATE`) the third. Any change means fresh certification: no skip, and the stamp does not match, so no fact row shows until a copy from the new database passes the load rule. A physical copy of the cluster run as a second live hub keeps all three and is unsupported (section 7's `hub_identity` addresses it later).

### 6.2 Replica

- **One copy, one mutex (F1).** Pull, dump, the capture drain's decision sync and the post-forget refresh all call one function, `hub_snapshot.copy_facts()`, which does all its work under one local file lock, `fact-copy.lock`, from opening the hub snapshot through the SQLite commit. Copies on one Mac are therefore serial, and each one's snapshot is taken after the previous one published, so a published copy is never older than the one it replaces; nothing compares xmin. The copy lock is outermost: no caller holds the memory lock or the registry `write_gate` when it takes it, so forget and the capture drain run the copy after releasing theirs (`forget.py` holds `memory_lock.exclusive()` for the whole forget). A waiter gives up after its remaining deadline or `REGISTRY_WAIT_S` and reports facts not refreshed; the last good copy stays.
- **What a copy reads**, in one REPEATABLE READ snapshot: `fact_copy_ready`, the incarnation, the change-token check, the `forgotten_sources` rows naming this Mac's registry strings (in hub form), the `episodes` rows named by bare registry ids, and, unless skipped, commitments, decisions and deliverables (only rows the hub's readers return) with fact vectors whose wording md5 differs from the held copy's (section 6 at `f3ab8344`, kept, including the vector's own chunk check and late vectors).
- **Skip (F8, owner answer 3).** The copy rewrites nothing, only re-checks the load rule, when the held stamp exists, the incarnation is the stamp's, `min(fact_changes.xid) <= pg_snapshot_xmin(S)`, and no `fact_changes` row with `xid >= pg_snapshot_xmin(S)` is invisible in `S`, where `S` is the stamp's stored `pg_current_snapshot()`. This never skips falsely under commit-order inversion (a late-committing older transaction is invisible in `S`), unlike a maximum sequence number; an empty `fact_changes` never skips.
- **Load rule.** A copy is published only if the `fact_copy_ready` row exists with `state = 'ready'`; every non-id registry string is a `forgotten_sources` row in the same snapshot; every bare id `N` is met, meaning the hub's episode `N` is tombstoned or absent in that snapshot (a read, never sent); the registry fingerprint at the SQLite commit equals the one taken before the hub read; the invalidation revision (below) at the SQLite commit equals the one taken before the hub read; and the stamp's destination (the configured hub endpoint) is the one copied from. Publication replaces the fact tables whole in one SQLite transaction under `write_gate`, and writes the stamp: fingerprint, incarnation, destination, `S`. A copy that fails the rule publishes nothing; the last good copy stays unless the stamp was cleared.
- **The stamp is the only visibility switch.** Readers compare the stamp's fingerprint with the current registry when SQLite runs the statement (`khipu_fact_epoch()`, kept) and show no fact row without a matching stamp. The stamp is cleared, in the same SQLite transaction, by anything that teaches this Mac a remote forget: an episode pull or live patch that writes a tombstone (`hub_snapshot.py:784`, `:5021`); a registry change needs no clearing, since it changes the fingerprint. Changing the configured hub endpoint clears it too (N3). So a remote forget learned before a failed copy hides facts at once (F5); the copy after it restores them.
- **Invalidation revision (N1).** A local counter, separate from the stamp, bumped in the same SQLite transaction (under `write_gate`) as every learned-tombstone stamp clearing above. `copy_facts()` reads it before opening the hub snapshot; a copy whose revision changed by publication publishes nothing, so a copy already in flight when a remote forget is learned cannot re-stamp its older snapshot. Facts stay hidden until a copy that started after the invalidation passes. Clearing and re-writing the stamp never resets the counter.
- **Forgets the hub lacks (owner answer 1).** Nothing is sent automatically. Registry strings the hub lacks (a backup import, a local outbox source, a forget whose hub transaction failed or timed out, a registry from before this design) are listed in the app's Activity pane and through `khipu_owner_act`, with facts hidden while any is listed. The owner's "Send to the hub" calls `refuse()` on their hub forms, in batches of at most 200 strings, each batch one transaction under the deadline; a batch that times out leaves its strings listed. A bare id `N` that is not met is listed with the hub episode `N`'s summary and two owner actions: "Forget it here" (an ordinary forget of that hub episode) or "Not the same episode" (removes `N` from this Mac's registry, logged). An id is never sent and never tombstones anything by itself, so a replacement hub's unrelated episode 42 is safe (F4).
- **Backups never carry fact rows or fact vectors.** `export_replica_copy` drops them, and a restore has no stamp until a copy.
- **Episodes and their vectors** keep main's fence by every identity of the row being imported.

### 6.3 Offline

- Forget needs the hub, as on main (owner answer 4): `forget_everywhere` opens the hub connection before it publishes anything, and refuses with a clear message offline. The local registry is published before `refuse()` (`forget.py:136`); if `refuse()` then fails or times out, the forget reports not done and its strings are listed (6.2).
- An offline Mac with nothing listed and an intact stamp shows its last copy. A forget made elsewhere that this Mac has not learned stays visible until it reconnects (the snapshot contract of section 6 at `f3ab8344`). One it has learned hides facts (6.2).
- A re-upload of a forgotten capture from this Mac's outbox, files or backup is refused by the hub triggers, legacy form included.

### 6.4 One operation deadline (F7)

A forget, an owner send and a copy each fix `deadline = time.monotonic() + FORGET_RETRY_BUDGET_S` (90 s) once. Before every blocking step the remaining time is recomputed, and a step that cannot fit is not started: connect (its `connect_timeout` is the remaining whole seconds, rounded down, and no connect starts with less than 2 s, libpq's floor); each lock and statement and the COMMIT (`SET LOCAL lock_timeout` and `statement_timeout` to the remaining milliseconds, rounded down, before each); each retry pause (`min(pause, remaining)`). Nothing rounds up and nothing has a minimum above the remaining time. Cancellation alone does not bound a stalled network (psycopg's `cancel_safe()` can itself stall, and success does not guarantee the query stops), so the bound is client-side abandonment (N4): the hub work runs on a worker thread; at the deadline the caller sends a best-effort cancel without waiting for it, shuts down the connection's socket (`socket.shutdown` on `conn.fileno()`), discards the connection (never reused), stops waiting, and releases its local locks. The worker never writes locally: every local publication (registry listing, SQLite copy) happens in the caller, and only from a result received before the deadline, so a late reply publishes nothing. Connect and this cleanup count against the same deadline. A commit whose outcome is unknown is not retried blind and not reported as rolled back or done: the strings stay listed, and a later copy's load rule reconciles them from the hub's snapshot (`refuse()` is idempotent). The local memory lock is held only while the deadline lasts.

### 6.5 Why each finding cannot recur

| Finding | Closed by |
|---|---|
| F1: an older copy published after a newer one | One copy function under one lock held from snapshot to SQLite commit; snapshots are serial, so order needs no comparison |
| F2: a refusal row trusted before history is indexed and swept | `fact_copy_ready` refuses `ready` until the pass covers every pre-migration id; the pass indexes and tombstones in one transaction per batch; no copy loads before `ready` |
| F3: direct refusal and carrier writes race | Database triggers take the identity lock on every refusal and identity write; mutations outside insert are refused; READ COMMITTED required |
| F4: a bare id replayed against a replacement hub | Ids are never sent or matched; an unmet id is listed for the owner and hides facts |
| F5: a learned remote forget leaves the old copy visible | A learned tombstone clears the stamp in the same SQLite transaction |
| F6: forget publishes co-carrier identities and loops | The refusal set is exactly what was asked; the inner step publishes nothing |
| F7: per-attempt timeouts exceed 90 s | One monotonic deadline for every connect, lock, statement, commit and pause, rounded down, with a cancel watchdog |
| F8: whole-copy cost | Exact skip when nothing changed; benchmark gate in phase 7B |
| Review 8 #1-#3 (Send scan, legacy barrier, partial Send) | Scan after the locks in the inserting transaction; legacy forms are refused rows; all carriers in one transaction |
| Reviews 2-7 replica P1s (contributors, re-fence, identity omissions, publication race, first-write certification, frozen fingerprint, delayed vector) | The replica derives no identity for facts; the stamp is set only by a copy that passed the load rule and read at execution time; vector wording hash kept |

The remaining limit: a hub episode holding the same capture under no identity the registry knows is treated as a different capture. Main's 0030 has the same limit.

## 7. Owner-write destination binding: a separate change

Owner-write destination binding shares no tables, locks or code with fact provenance, so it ships separately. Coupling the two on one branch produced the second review's P2-2 and the third review's #1 and #4, which were judged together with unrelated fact defects. The rules for that change:

- The hub gets a random `hub_identity` uuid (its own migration). An endpoint fingerprint cannot tell a recreated database at the same address.
- New entries bind that uuid, and replay checks it on the connection that applies the write.
- An entry with no binding is never applied. It moves out of the ordered queue into `unbound/`, so it does not hold up other writes. A later write to the same record id waits behind it. The app lists it with two owner actions: "send to this hub" (an explicit bind; the receipt is checked first) and "discard".
- Clear takes the entry claim before reading, then re-reads. An entry already applied or missing is reported as such.
