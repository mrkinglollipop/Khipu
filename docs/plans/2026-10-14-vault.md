# Vault: a bot logs into websites for the owner, with no one in the loop

Asked by Matt 2026-10-14 ("I want grok bot to be able to access my iCloud Keychain passwords so it can
logon into websites for me without me having to get involved"; "I like it. Scope it. What about passkeys?").
This page is the scope; a build session reads it first. Builds after the promotion gate and plan usage and
goes through the gate.

## Status

| Phase | What | State |
|---|---|---|
| 1 | `khipu vault`: a Khipu-owned Keychain store, one-time import from the Passwords app, per-bot site allowlist, the `khipu_login` broker that fills a login in the bot's browser session, TOTP, audit episodes, lock switch | open |
| 2 | Passkeys: bot-owned software passkeys per site through the browser's virtual authenticator, keys in the vault | open, see "Passkeys" |
| 3 | Settings page for the vault: entries (names only), allowlists, last uses, lock | open |

Three PRs. Phase 1 first. First target is a bot with a browser on this Mac; Grok Bot's cloud box is served by the
session hand-off and its own 1Password connection (see "Where the broker can and cannot reach").

## What was established (this Mac, macOS 27.0.1, 2026-10-14)

- **iCloud Keychain website passwords are unreachable to a background process.** The `security` search list
  holds only `login.keychain-db` and the System keychain; the iCloud (data-protection) keychain is not in
  it, and the one `github.com` item visible from the command line is a git credential in the login keychain,
  not a Safari login. Apple hands website passwords only to Safari, the Passwords app and credential-provider
  extensions, each fill behind Touch ID or a consent sheet. No API, entitlement or automation path reads them
  silently, so "no one in the loop" cannot be built on the iCloud Keychain itself.
- **Khipu's own Keychain items can be read by its binaries without a prompt** once the owner marks them
  "always allow" at setup (how `khipu secrets` keys work today, `keychain.py`). That is the store.
- **Grok Bot's browser is not on this Mac.** `/Applications/Grok Bot.app` (0.70.2, bundle `com.anysphere.sand`)
  is a thin Electron client; its browser runs in a remote Linux "box" that xAI hosts (Khipu's own
  `gateway.py` and `integrations.py` already call it an ephemeral Linux VM; the app's strings name the
  box's `vncUrl`, `gatewayUrl`, `execDaemonUrl`, `/opt/sand`, and "box Chrome CDP"). The box's Chrome is
  reachable only from inside the box. The app also ships a Mac-side computer-use helper (Accessibility and
  screen capture, drives apps on this Mac) and a local exec daemon. Grok Bot already has credential
  plumbing of its own: a 1Password connection (it mints a read-only service-account token for one vault,
  the box runs 1Password's extension, fills need the owner's approval each time), a per-origin cookie
  import approved on the desktop and injected into box Chrome, and a reverse WebAuthn channel that signs
  box passkey ceremonies on the Mac with a physical security key after a consent prompt. Researched
  2026-10-14 from the bundle; xAI publishes no architecture doc.
- **1Password's agentic autofill (2025-10, Browserbase; 2026-07, Claude in Chrome; used by Grok Bot)** is
  the industry shape: the agent asks for a login, a human approves every fill on the 1Password device by
  Touch ID, the value travels on an end-to-end channel to the 1Password extension inside the agent's
  browser, which fills and submits, and the agent gets only success or failure. Username, password and
  TOTP; no passkeys; no unattended mode.

## Where the broker can and cannot reach

| Bot and browser | Khipu broker fills it? | How |
|---|---|---|
| A bot driving a browser on this Mac (Aegis personal bot, Claude in Chrome, Grok Bot's Mac computer-use sessions, any local Chrome with a debugging port) | Yes, unattended | the design below: CDP fill, value never in the model |
| Grok Bot's cloud box browser | No direct fill: the box's Chrome is not reachable from the Mac | two supported routes, both through Grok Bot's own channels: (1) Grok Bot's 1Password connection, one Touch ID approval per fill; (2) session hand-off: Khipu logs in on the Mac in a local Chrome profile, Grok Bot's cookie import carries the session into the box, one approval per origin on the desktop. A third route, delivering the secret into the box, puts it in a VM the model and the vendor control and is outside this scope. |

Matt's goal is no one in the loop. For every local browser that goal is met. For the cloud box it is not
met by anyone today: 1Password keeps an approval on every fill on purpose, and xAI's cookie import keeps
one per origin. The only way to remove the human from the box is to hand the password to the model, which
is the one thing this scope refuses to do; if Matt decides that trade is worth it for named sites, it is
a separate decision recorded here, not a default.

## Design

**Store.** `khipu vault import <csv>` reads the Passwords app export (File → Export, the app asks for the
login password once), writes one Keychain item per entry under service `khipu-vault` (account = site, with
username, password and, when present, TOTP seed and notes), shreds the CSV, and lists what it imported by
site name only. Items are local Keychain items: not iCloud-synced, not in the memory git sync, not in the
hub, not in any Khipu backup. `khipu vault add|remove|list` manage entries by name; `list` never prints a
value. A site may hold several accounts, selected by username.

**Broker.** The bot never receives a password. It gets one tool, `khipu_login` (MCP) / `khipu vault login`
(CLI), with `{site, username?, session}` where `session` names a browser automation endpoint the bot owns
(a Chrome DevTools Protocol target or a Playwright context; the first build supports CDP, which is what a
locally run Chrome exposes with `--remote-debugging-port`; for Grok Bot's cloud box the broker's job is the
session hand-off above, never a fill). The broker finds the login form on the current
page, fills username and password through the automation layer, submits, and when a one-time-code field
appears fills the current TOTP from the stored seed. It returns `{ok, site, username, landed_url, steps}` and
nothing else. If the page shows a CAPTCHA or a challenge the broker does not recognise, it returns
`{ok: false, reason: "challenge"}` and stops; Khipu never attempts to solve one.

**Allowlist.** Config `vault_allow: {<bot>: [<site>, ...]}`, where bot is the harness identity Khipu already
knows (`grok_bot`, `aegis`, `claude_code`, ...). A request outside the list is refused and logged. Default:
empty, so nothing is usable until the owner names sites.

**Audit.** Every call, allowed or refused, becomes an episode: bot, site, username, time, outcome,
landed URL. These are ordinary memory and are searchable; they never contain a value. The health report shows
the last ten uses and the refusal count for the day.

**Lock.** `khipu vault lock` makes every item unreadable until `khipu vault unlock` (the ACL is reset so
the next read prompts the owner). Doctor shows locked/unlocked.

**Risks the owner accepts, written here once.** A page or message the bot reads can steer it into logging
into a site on its list (prompt injection); the allowlist bounds this, nothing removes it. Sites with bot
detection will challenge; the broker stops there. Some terms of service forbid automated login. A second
copy of the passwords exists on this Mac; it is protected by the login keychain and the Khipu binaries'
"always allow" ACL, which means any process that can run those binaries as the owner can read them.

## Passkeys (researched 2026-10-14; Apple and Chrome docs read that day)

**The owner's passkeys cannot be handed to a bot.** An iCloud Keychain passkey signs only inside Apple's
platform authenticator (`ASAuthorizationPlatformPublicKeyCredentialProvider`; the browser-facing manager
needs an entitlement), through the Secure Enclave, behind Touch ID or the account password every time; no
entitlement, AppleScript, Accessibility or `security` path satisfies that check. Google Password Manager
passkeys on a Mac are unlocked by the screen lock and a device PIN the same way. Credential Exchange export
shipped in macOS 26 (`ASCredentialExportManager`, FIDO CXF 1.0, passkey private keys as PKCS#8), but it is a
one-time, user-authenticated, app-to-app transfer to an installed credential-provider app that declares
`SupportsCredentialExchange`; Apple Account passkeys are excluded, and whether a Developer ID app outside
the App Store gets that entitlement is unconfirmed. It is not a login path and the vault does not depend
on it.

**The route that works headless: the bot owns its passkeys.** Chrome DevTools Protocol `WebAuthn` domain
(experimental, last changed 2026-08-28): `WebAuthn.enable`, `addVirtualAuthenticator` (ctap2, internal,
resident key, user verification, `isUserVerified` and `automaticPresenceSimulation` true), then the site's
own registration flow creates a passkey in that authenticator. `getCredentials` returns the credential id,
RP id, user handle, sign count and the ECDSA P-256 private key in PKCS#8; `addCredential` loads one back.
The browser still enforces origin and RP id, so real sites accept it; sites that demand attestation or a
particular authenticator model refuse it, and the broker reports that as a challenge. The authenticator
lives only for the CDP session, so the vault is the durable store.

Phase 2 builds: `khipu vault passkey register <site>` (the broker drives the site's "add a passkey" page
in the bot's browser with a fresh virtual authenticator, then stores the credential record as a vault item,
the same way a password is stored); at login, `khipu_login` creates a virtual authenticator, adds the
stored credential, lets the site's passkey prompt complete, and writes the sign count back. The owner's
own passkeys on their devices are never touched; the bot's passkey is one more entry on the site's
account, removable there at any time. Playwright and Puppeteer reach the domain only through a raw CDP
session; Safari WebDriver support is unconfirmed, so phase 2 is Chrome-family only.

## Decisions

- Broker, not vault access: the bot acts through Khipu; it never holds a credential, so a compromised bot
  session leaks a login event, not a password. This is also why the cloud box gets a session, never a
  secret: the box is the model's machine.
- Khipu's own Keychain items, not a new encrypted file: the OS already protects the store and the ACL, and
  `khipu secrets` already works this way.
- Local only, never synced or backed up with the memory: the memory pipeline crosses third-party models and
  a remote hub by design; the vault must not.
- CAPTCHAs and challenges end the attempt: Khipu does not bypass bot detection for anyone.
