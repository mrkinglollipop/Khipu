# Work: the ledger of what is done and not done, and a live view of every project

Asked by Matt 2026-10-15: "an app that shows across all of my repos a live tracking of what's going on as
well as a status board for each one ... Khipu could become almost like the house of the SSOT for
everything." Amended the same day: "the work view ... does or holds the ledger that we're using inside of
repos for keeping track of what work is done versus not. Khipu becomes the SSOT for that." This page is the
scope, approved by Matt on 2026-10-15 with the mocks; a build session reads it first. The mocks are in `docs/mockups/2026-10-15-work-view/`. It builds on
routing truth (`2026-10-14-routing-truth.md`: the read-only runner reader, the account record and the Home
Routing card), and every phase reaches this Mac only through the promotion gate
(`2026-10-14-promotion-gate.md`).

**What Matt gets, in plain words.** A Work tab in the Khipu app. At the top, one list of everything only he
can do, across every project, oldest blocker first, each closable on the spot. Under it, every job running
right now in any project: which account and model, for which pull request or task, for how long, and one
short line on what it is doing. Then the accounts, in the same rows as Home. Then a board per project: its goals and how
far each has got, its loose ends, its pull requests with the stage each is at and the first line of its last
verdict, its release trains and their test runs, and what merged this week. Behind each board, that
project's full ledger: every goal, slice, review and loose end with its state and its whole history, which
Matt can change in the app. A phone or web view can come later and read the same data.

The scope has two parts. **Part A, the ledger, is the core**: Khipu holds the record of what work is done
and what is not, written by conversations through Khipu and by Matt in the app. **Part B, the live view**,
reads what each project's job runner says it is doing right now, and only reads.

## Source facts (2026-10-15)

- **The trackers today.** Two orchestrators each keep a copy of the same stdlib tracker script (415 lines; the
  copies differ only in their home folder and their kind list) over one JSON store, `{"rows": {id: row}}`.
  Every row has exactly `id, title, kind, parent, state, evidence, owner, updated, history`; every history
  entry has exactly `ts, from, to, note`. States: VERIFIED, MERGED-UNVERIFIED, BUILT-UNMERGED, IN FLIGHT,
  QUEUED, NOT STARTED, NEEDS MATT, DROPPED, DONE. Kinds across both: goal, slice, review, loose-end,
  needs-matt, audit-item, drive, wave, train. Verbs: add, set, get, list (state, kind, owner, stale hours),
  loose-ends (`--summary`), needs-matt, render (a markdown board), check.
- **Their size.** One store holds 1,033 rows and 2,586 history entries (1.27 MB), the other 644 rows and
  1,736 entries (0.55 MB). Ids are at most 41 characters of letters, digits and `._:/-`. Titles run to 1,366
  characters and evidence to 529. Six rows name a parent that does not exist. 73 rows are NEEDS MATT.
- **What they lose today.** `set` writes the whole file with no lock, so two agents writing at once can lose
  one write. A change of evidence or owner adds a history entry that says "updated fields" but not the old
  value, so earlier evidence is gone. History entries carry no author. The store lives in one place, outside
  any backup Khipu runs.
- **Khipu's storage.** Memory lives in the hub database (Postgres, `ops/migrations/`, latest `0026`), with a
  nightly dump, an off-site copy, the offline copy for reads when the hub is away (`khipu/hub_snapshot.py`),
  and a durable outbox for captures that could not reach it (`khipu/outbox.py`; doctor is red while it holds
  anything). Commitments are a hub table keyed by project (`khipu/commitments.py`), and "needs the user" is
  `owner == "user"`. The routing record is a state file pair with its own lock (`khipu/routing.py`), and its
  job runner reader opens runner files read-only (`khipu/routing_sources.py`).

## What Khipu does and does not do

Khipu **keeps the ledger and shows the work**. Conversations write ledger rows through Khipu, and Matt writes
them in the app; Khipu records who wrote each change and never loses one. Khipu never routes, starts, stops,
retries, reorders, merges, approves or answers anything on a project's behalf. It never writes a project's
files, never takes a runner's lock and never runs a command in a project. Khipu never changes a ledger row on
its own judgment: it does not mark work verified, close a loose end, or infer a state from a pull request.
A decision a runner or a pull request is waiting on is made where it lives; the Work view shows the ask and
opens the link.

## Rules (hard constraints, carried into every phase)

1. **The live view only reads.** Part B never writes a project's files and nothing in it sends anything to a
   project or a runner, or changes where work goes. The ledger is written only by the callers the scope names
   (conversations and job runners through `khipu ledger` or `khipu_ledger`, and Matt in the app), never by
   Khipu itself. Purging a removed row after 30 days is the one thing Khipu does on a timer, and only to a row
   a writer already removed.
2. **Everything in the app.** Every owner action (change, remove or restore a ledger row, close a need, add or
   remove a project,
   choose its file, import a tracker, change a limit, hide or unhide an item, close or snooze a commitment,
   confirm a rule) is done in the app. No phase hands Matt a terminal step. The CLI exists for agents, tests
   and doctor.
3. **No secrets, no portfolio data.** No key, token or credential is ever stored or shown. A file under a
   credential location (`API Keys/`, `My Portfolio/`, a keychain, any `auth.json`) is refused and never
   opened, using the routing reader's `private_path`. Khipu's secret redaction runs over every string it
   keeps: a ledger write that trips it is refused with "This looks like a key or password; nothing was saved";
   a summary field that trips it is left out whole, never shown masked.
4. **Titles only.** Ledger rows and summaries carry titles and short plain-words lines about the work, never a
   project's private data: no code, diffs, file contents, command output, logs, prompts, briefs, customer or
   financial details. Writers are responsible; Khipu enforces what it can (lengths, kinds of value, links,
   paths cut to their last name).
5. **No loss, with one owner-sanctioned exception.** No ledger change is destructive except a remove: DROPPED
   is a state and keeps the row, every change appends history with the old value of every field it changed, a
   write that cannot reach the hub waits in the outbox, and the import loses nothing (verified by counts and a
   round trip). Remove (below) exists because a row that should not exist must be able to go; it is always a
   writer's explicit act, restorable for 30 days, and never automatic: Khipu never removes a row on its own
   judgment.
6. **Rows never reorder under the reader.** Every ledger listing orders by kind, then parent group, then the
   order rows were added; never by state or by last change.
7. **Every limit can be lifted in the app.** Every size cap, count cap and staleness time below is a setting
   with a Change… button; 0 means no limit wherever a limit makes sense. The one exception is the job status
   line (one line of about 90 characters, up to 3 when opened): that is Matt's design for the view, not a limit
   on work, and its only switch is hiding it.
8. **Plain words.** Every string the app shows is plain language for a non-technical owner, with local times.
   No em-dashes in any UI string.
9. **One read model, nothing desktop-only in the data.** The desktop renders documents Khipu builds; anything
   a phone or web view will need is in them, and nothing in them depends on the desktop (no paths, login
   folders, account keys or pre-formatted local times).

## Part A: the ledger

### Where it lives: the hub database

**Decision: the hub database, not a state file.** The ledger is memory-grade data and must survive like
memory does. The hub already has what that takes: the nightly dump and off-site copy, the offline copy for
reads when the hub is away, the outbox for writes when it is away, transactions for many writers at once, and
the gateway a phone, web view or cloud agent would later reach. A state file (the routing record's shape)
would need its own backups, its own lock across processes and its own copy for the hub, and would still be
on one Mac. The cost: a write needs the hub or the outbox, and Postgres must be set up, which every Khipu
install that captures memory already has.

Migration `0027_ledger.sql`:

- `ledger_rows`: `project`, `row_id`, `title`, `kind`, `parent` (a row id or empty), `state`, `owner`,
  `evidence`, `link` (https or empty), `refs` (jsonb: `pr`, `train`, `commitment`), `seq` (the order the
  row was added in its project, never changed), `created_at`, `updated_at`, `version` (counts changes).
  Primary key `(project, row_id)`.
- `ledger_history`: `id`, `project`, `row_id`, `at` (Khipu's clock, or the original time for imported
  entries), `by` (set by Khipu, never taken from the caller: a conversation's harness, project and session;
  "a job runner in <project>"; "you, in the app"; "imported, author not recorded"), `from_state`, `to_state`,
  `changes` (jsonb: each field changed, with old and new value), `note`, `op_id` (unique; makes a retried
  write harmless), `source` (cli, mcp, app, import).
- `ledger_projects`: `project`, `name`, `created_at`, and one row per import (`ledger_imports`: when, the
  source file's name and digest, the counts read and written, the result).
- `ledger_rows` also carries `removed_at`, `removed_by` and `removed_note` (empty unless removed).
  `ledger_removed`: `project`, `row_id`, `by`, `at`, `purged_at`; the bare marker a purged row leaves behind.
- Added to the offline copy (`hub_snapshot`) and to the nightly dump's table list; doctor checks both.

There is no plain delete. A row leaves the ledger only through remove and its purge, below.

### Removing a row

DROPPED and remove are two different things. **DROPPED** is "won't do": the row stays, with its history,
and is hidden from open lists, as today. **Remove** is for a row that should not exist at all: written by
mistake, a duplicate, or holding something that must not be kept.

- **Who.** Any writer: a conversation through `khipu ledger remove <id> [--note N]` or `khipu_ledger` verb
  `remove`, or Matt in the app. `khipu_forget` on a ledger id does the same as remove.
- **At once.** A removed row disappears from every list, render, count, push, Waiting on you, the read model
  and the offline copy. `get` on it says "row X was removed on <date> by <who>".
- **Restore for 30 days.** The app keeps a Removed list (Settings → Work → Removed rows, and a link on each
  project's ledger page) where Matt can restore a row; it comes back with its history and one more entry,
  "Restored by you, in the app". Restore is an owner action in the app only.
- **Purge.** After 30 days the nightly purges the row and its history text, leaving only a bare marker in
  `ledger_removed` (project, id, who removed it, when). Matt can also choose Remove for good in the app, which
  purges at once after a confirmation that says it cannot be undone. The marker means an import, a catch-up
  or a retried write never brings the row back: an `add` or import of a purged id is refused with "row X was
  removed for good on <date>".
- **Children.** Removing a row with children asks what to do with them: remove them too, or move them up to
  the removed row's parent. The CLI and MCP tool require `--children remove` or `--children move-up` when the
  row has children, and refuse otherwise.
- **The removed text in backups.** The nightly dump and off-site copy taken before a purge still hold the
  row until they age out; the app says so beside Remove for good.

### Projects

A ledger project is the same project key commitments use, so a project's ledger rows, its commitments and
its board line up. The CLI and MCP tool take the project from the working folder exactly as capture does,
and `--project` overrides it. A project appears in the ledger when its first row is added or imported; Matt
can rename it for display and hide it in Settings → Work, never delete it.

### Rows, states and kinds

Fields and limits, each a setting (`ledger_*`, Change… in Settings → Work, 0 for no limit):

| Field | Rule |
|---|---|
| `row_id` | `^[A-Za-z0-9][A-Za-z0-9._:/-]{0,79}$`, unique in its project, never changed |
| `title` | one line, at most 2,000 characters (`ledger_title_chars`); never clipped on write: a longer title is refused with its length and the limit |
| `kind` | goal, slice, review, loose-end, needs-owner, audit-item, drive, wave, train (`needs-matt` is accepted and stored as needs-owner) |
| `parent` | a row id in the same project, or empty; a parent that does not exist is kept and shown as "Parent not found" |
| `state` | the nine below; a new row starts NOT STARTED |
| `owner` | a short name, default "none"; the app shows rows with no owner as "No one" |
| `evidence` | one line, at most 1,000 characters (`ledger_evidence_chars`); a PR number, a commit, a test result |
| `link` | optional https link to where the work or the decision lives (query and fragment dropped) |

States, with the words the app shows:

| Stored | CLI word | App words | Open or finished |
|---|---|---|---|
| verified | VERIFIED | Verified | finished |
| merged-unverified | MERGED-UNVERIFIED | Merged, not verified | open |
| built-unmerged | BUILT-UNMERGED | Built, not merged | open |
| in-flight | IN FLIGHT | In progress | open |
| queued | QUEUED | Queued | open |
| not-started | NOT STARTED | Not started | open |
| needs-owner | NEEDS OWNER (also accepts NEEDS MATT) | Needs you | waiting on Matt |
| dropped | DROPPED | Dropped | finished |
| done | DONE | Done | finished |

The public product ships the word NEEDS OWNER; the setting `ledger_owner_word` lets this Mac print NEEDS
MATT so existing callers and their parsing keep working. A loose end is any row whose state is open (the old
tracker's rule: everything except VERIFIED, DONE, DROPPED and NEEDS MATT).

### Verbs: `khipu ledger` and `khipu_ledger`

The CLI takes the tracker's verbs and flags unchanged (remove is new), so an orchestrator switches by replacing
`python3 tracker.py` with `khipu ledger` and nothing else:

```
khipu ledger add <id> --title T --kind K [--parent P] [--state S] [--evidence E] [--owner O] [--note N] [--link URL]
khipu ledger set <id> [--state S] [--evidence E] [--owner O] [--note N] [--title T] [--link URL] [--if-state S]
khipu ledger get <id>
khipu ledger list [--state S] [--kind K] [--owner O] [--stale-hours N]
khipu ledger loose-ends [--summary]
khipu ledger needs-owner            (needs-matt is the same verb)
khipu ledger render [--out FILE]    (the markdown board; stdout unless --out)
khipu ledger check
khipu ledger remove <id> [--note N] [--children remove|move-up]
```

Every verb also takes `--project P` and `--json`. The printed lines keep the tracker's shapes ("added X:
STATE", "set X: state, evidence", the `id · STATE · title · owner=… · updated=…` list lines and the
closing counts), so a caller that parses them keeps working. The MCP tool `khipu_ledger` takes `verb` plus
the same fields as JSON and returns JSON; its description carries rule 4 so callers see it. `khipu_status`
gains a `ledger` line (rows, loose ends, needs-owner, outbox).

Write rules:

- `add` of an id that exists fails ("row X already exists; use set to update it"), as today.
- `set` records the old and new value of every field it changes, and a note alone is an entry of its own.
  `--title` and `--link` are new; `kind`, `parent` and `row_id` stay fixed after `add`, as today.
- `--if-state S` makes the write happen only if the row is still in state S; otherwise it fails with the
  current state and who set it. This is how two agents avoid overwriting each other.
- `check` reports rows with a state or kind Khipu does not know, no owner, a missing parent, or open for
  longer than `ledger_stale_after` (default 7 days), and exits non-zero only for the first two, as today.

### Many writers at once

Each write is one database transaction: the row is locked (`SELECT … FOR UPDATE`), its history entry is
appended, and the row is updated, so no write is lost and history order matches the order writes landed.
Without `--if-state`, the later of two writes is the row's value and both are in its history. Every write
carries an `op_id` (generated by the caller's Khipu, or passed in for a retried call), so a retry after a
timeout never writes twice.

### When the hub is away

A write that cannot reach the hub goes to the ledger outbox (`<data dir>/ledger-outbox/`, one file per
write, written to a temp file and renamed, like the capture outbox) and the caller is told "Saved on this Mac;
it reaches the ledger when the database answers". The outbox drains on the next ledger call that reaches the
hub, at each Stop hook and nightly. A queued `set` with `--if-state` that no longer matches when it drains is
still recorded, as a history entry marked "arrived late; the row had moved to <state>", and the row is not
changed; nothing is dropped. Reads while the hub is away come from the offline copy with the waiting writes
applied on top, marked "as of" the copy's time. Doctor is red while the ledger outbox holds anything, and the
app shows "3 ledger changes are waiting for the database".

### Importing an existing tracker

Import is an owner action in the app (Settings → Work → Ledger → Import a tracker…), with `khipu ledger
import <file> --project P [--dry-run]` behind it for tests:

1. Matt chooses the tracker's JSON file and the project. Khipu reads it read-only (the routing reader's open,
   the private-folder refusal, no size limit for import because the no-loss rule wins) and shows what it
   found: rows by state and kind, history entries, rows with a missing parent, rows whose id already exists
   in that project, and any field that trips secret redaction. Nothing is written yet.
2. Import writes every row and every history entry in one transaction, keeping each entry's own time, from,
   to and note, with `by` "imported, author not recorded" and source import. Each row then gets one more
   entry, "Imported from <file name> on <date>". The tracker's `updated` becomes the row's `updated_at`, and
   rows take `seq` in the tracker's own render order (kind, then parent, then id), so the board reads as
   it did. Kinds and states outside the lists above are imported as they are and flagged by `check`; nothing
   is coerced. A field that trips redaction is stored with that part masked, the row is listed in the import
   report, and the unmasked original stays only in the old file.
3. Verification, shown in the app and stored with the import: counts of rows, history entries, rows per state,
   per kind and with a parent, compared source against ledger; and a round trip: `khipu ledger export
   --tracker-json` for that project, compared field by field with the source file. The import is marked done
   only when every count matches and the round trip differs only where the report says (masked fields).
   Otherwise the transaction is rolled back and the report says what differed.
4. Ids that already exist: the import refuses and lists them; Matt chooses a different project or imports into
   a new one. Re-importing the same file is a no-op ("Nothing new: every row and history entry is already
   here").

**Catching up.** After import, an orchestrator still running the old script can write to the old file. Khipu
keeps the file's digest and, while Settings → Work lists the file, checks it on each Work refresh. If it
changed, Work shows "The old tracker for <project> changed after it was imported: 4 new history entries" with
Bring in the changes, which imports only entries newer than the last import (matched by row id, time, from,
to and note). A change to a row Matt or a conversation has since changed in Khipu is brought in as history
and shown as "changed in both places" for Matt to settle in the app; Khipu never picks a winner silently.

**The old files afterwards** are kept where they are, and Khipu never writes, moves or deletes them. Phase 6,
in each project with Matt's go, replaces the project's `tracker.py` with a few lines that hand every verb to
`khipu ledger --project <key>`, so old call sites keep working, and keeps the old `tracker.json` beside it
untouched as the pre-import record. Making the file read-only would not stop the old script (it replaces the
file by rename), which is why the forwarding script and the catch-up check exist.

### Changing a row in the app

On a project's ledger page each row opens to its detail: every field, its parent and children, and its
whole history, newest first, each entry with who, when, from, to, the fields changed and the note. Matt can:
change the state (a menu of the nine words), add a note, edit the evidence, owner, title or link, and, on a
Needs you row, use Done, Drop or Answered (sets a state Matt chooses, default DONE, with his note). Every
change is written through the same path as the CLI, with `by` "you, in the app", and shows in the history at
once. Remove… is on every row's detail, apart from the change form, and asks about children when there are
any. There is no reorder.

## Part B: the live view

### Where the data comes from

1. **Each project's summary file** (`work-summary.json`, format below), written by that project's job runner
   and read by Khipu read-only, exactly as routing reads runner folders: opened `O_RDONLY | O_NONBLOCK`, a
   regular file only, size checked before reading, no lock, no temp file, the private-folder check before
   anything is opened (`routing_sources.read_only` is the analog and is shared, not copied).
2. **The ledger** (part A), for goals, loose ends and Needs you rows.
3. **Khipu's own open commitments marked "needs the user"** (`commitments.list_owed`), across every project.
4. **Khipu's routing record**: standing rules that are pending or seeded and not yet confirmed, Matt's holds
   at their reminder, and the accounts.

### PR stages and trains: in the runner's summary, not the ledger

**Decision.** A pull request's stage (built, checking, fixing, cleared, flagged, merged) and a train's test
runs come from the runner's summary file. The ledger holds the orchestrator's durable claims about work
(a slice is BUILT-UNMERGED, MERGED-UNVERIFIED, VERIFIED), which can name a pull request in `refs.pr`. Why:

- The runner is the authority on stages and runs; it changes them every pass. Copied into the ledger they
  would either flood its append-only history (a pass every 20 seconds) or go stale without saying so.
- Stages are machine facts with no owner decision in them; the ledger's states are judgments ("verified"
  needs someone to have checked), which only a conversation or Matt may write (rule 1).
- Keeping them apart lets the board say when the two disagree instead of hiding it: a ledger row that names
  pull request 41 as BUILT-UNMERGED while the runner says 41 merged shows "The runner says this merged; the
  ledger still says built, not merged". Khipu does not change either side.

Trains follow the same reasoning; a ledger row of kind train can name the runner's train in `refs.train`.

### Registering a project's summary file

Setting `work_projects`, a list of at most 64 entries `{project, name, file, on, show_now}`, edited only in
Settings → Work:

- **Add a summary file…** asks for the project (from the ledger's projects, or a new one) and the file
  (Choose file…, or type its full path). Before saving, Khipu reads the file once and shows what it found
  ("Found 3 jobs, 12 pull requests and 1 release train, updated 8 s ago") or why it could not read it; Matt
  can save either way. The file's `project.id` must match.
- **Suggested.** For each routing job runner folder (`routing_sources`) that holds `state/work-summary.json`,
  Settings offers "Add <runner name>" with that file filled in. Nothing is added without Matt's click.
- Each can be turned off (kept, not read), removed, and set to hide what its jobs say they are doing
  (`show_now`, on by default).
- A path must be absolute, is refused under a credential location, and is shown only in Settings, never in
  the read model.

least every time something in it changes and at least once per `runner.interval_s` while the runner is

`docs/formats/work-summary-1.schema.json` (phase 3) and `khipu work check <file>` validates a file for runner
authors.

```json
        { "name": "Device tests", "state": "running", "at": "2026-10-15T19:29:00Z" }
      ],
      "summary": "Waiting for 41 before the device run can finish"
    }
  ]
}
```

**Top level.** `format` must be `"khipu-work-summary"`. `version` is an integer; Khipu reads 1. Fields added
inside format 1 are optional and ignored by an older Khipu; a change that would break an older reader bumps
the version, and Khipu shows a newer version as "written in a newer format" without reading its items.
`written_at`, `project.id` and `project.name` are required; `runner` and every list are optional (a missing
list is an empty list). Unknown keys anywhere are ignored and never kept.

**No waiting list in the file.** The brief asked for `waiting_on_owner[]`; the ledger replaces it. A runner
that needs Matt adds a NEEDS OWNER row through `khipu ledger add` (one write through Khipu, the same as a
conversation), because an item in a read-only file is one Matt could never close in the app, and two places
to put a need would mean duplicates. A `waiting_on_owner` key in a file is ignored and counted in doctor
("this file has a waiting list Khipu no longer reads; add those as ledger rows").

**Values.** Times are RFC 3339 with `Z` or an offset. Ids match `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$`. Every
item carries `project`, which must equal `project.id`; an item that names another project is left out. Text
fields are single lines: control characters are removed, runs of spaces collapse, any path-like token is cut
to its last name, and each is clipped to its cap. A `link` is kept only when it is `https`, and only its host
and path. Labels (`account`, `model`, `lane`, `by`) must pass routing's `safe_name` shape check.

| List | Required per item | Optional | States (in the app) |
|---|---|---|---|
| `jobs` | `id`, `project`, `state`, `started_at`, `updated_at`, `summary` | `kind` (build, check, fix, review, test, release, other), `for` (`pr`, `train`, `ledger` (a ledger row id), or `task`, a title of at most 80 characters), `account`, `model`, `lane`, `ended_at`, `now` (at most 3 status lines, oldest first, each `{at, text}`, text at most 90 characters) | queued "Waiting to start", running "Running", waiting "Waiting", done "Finished", failed "Stopped with a problem", stopped "Stopped" |
| `prs` | `id`, `project`, `title` (at most 120), `stage`, `stage_at` | `opened_at`, `merged_at` (required when merged), `verdict` (`outcome`: cleared, flagged or unclear; `first_line` at most 200; `by`; `at`), `link`, `summary` | built "Built", checking "Being checked", fixing "Being fixed", cleared "Cleared", flagged "Flagged", merged "Merged", closed "Closed without merging" |
| `trains` | `id`, `project`, `name` (at most 40), `state`, `updated_at` | `prs` (ids), `runs` (each `name` at most 60, `state`, `at`, optional `summary`), `summary` | open "Gathering changes", testing "Testing", blocked "Held up", shipped "Shipped", dropped "Dropped"; runs: queued, running, passed, failed, skipped |

A value Khipu does not know in a state field keeps the item and shows "State not known to this Khipu"; a
missing required field or a bad id drops that one item, which is counted ("2 items couldn't be read and are
left out"). One bad item never hides the rest.

**What a runner writes in `now`.** Its own plain status line for the job: the general gist of what the job is
doing, in about 90 characters, written by the runner. It is never a feed of the session's narration, and
never tool output, file contents or commands. The runner keeps the last 3. Khipu cleans each line as above
and clips it at 90 characters. The job's row shows only the newest line; opening the job shows up to the
last 3. Nothing longer is ever shown. Matt asked for this on 2026-10-15: "knowing a general gist of what
it's doing is good, but we definitely don't want it getting clunky and clogged up with a bunch of
verbiage." Matt can hide the line per project (`show_now`).

**What a runner keeps in the file.** Running and queued jobs; jobs that ended in the last hour; open pull
requests and those merged or closed in the last 7 days; open and testing trains and those shipped in the last
7 days. Khipu applies its own windows too (below).

### Caps, staleness and what Khipu shows

Every value here is a setting in Settings → Work with Change…. Defaults:

| Setting | Default | What happens past it |
|---|---|---|
| `work_file_max_bytes` | 256 KB (0: no limit) | the file is not read; its last good read shows with "The summary file is 412 KB, over the 256 KB limit" and Raise the limit |
| `work_max_jobs`, `work_max_prs`, `work_max_trains`, `work_max_runs` | 50, 200, 20, 20 per project (0: no limit) | the newest are kept; "Showing the newest 50 of 64 jobs" with Raise the limit |
| `work_line_chars` | 200 (0: no limit) | longer summary text is clipped with an ellipsis (ledger text is never clipped, only folded in the view) |
| `work_stale_after` | automatic: five of the runner's intervals, at least 2 minutes; 10 minutes when the file names no interval | "No update for 23 min; showing what it said at 3:17 PM" |
| `work_job_quiet_after` | 15 minutes | a running job says "No word from this job for 18 min" |
| `work_gone_after` | 24 hours | the board folds to "Not reporting since Tue 4:10 PM", and its jobs leave Running now |
| `work_finished_for` | 30 minutes | ended jobs leave "Just finished" |
| `work_merged_for` | 7 days | older merges leave "Merged this week" |
| `work_clock_slack` | 5 minutes | a time further ahead of this Mac's clock is shown as now and counted in doctor |
| `work_refresh` | 5 seconds | how often the open Work tab asks for the view |
| `ledger_stale_after` | 7 days | an open row unchanged that long shows "No change for 9 days" |

Each summary source is in exactly one of these states, shown on its board and in Settings:

| Source state | When | The app says |
|---|---|---|
| ok | read and fresh | "Updated 12 s ago" |
| stale | `written_at` older than `work_stale_after` | "No update for 23 min; showing what it said at 3:17 PM" |
| gone | older than `work_gone_after` | "Not reporting since Tue 4:10 PM" |
| missing | no file at the path | "No summary file yet at the place you set." with Open Settings |
| too big | over `work_file_max_bytes` | "The summary file is 412 KB, over the 256 KB limit." with Raise the limit, plus the last good read |
| unreadable | not JSON, wrong `format`, missing top-level fields | "Couldn't read the newest summary; showing what it said at 3:05 PM." Errors are fixed phrases, never the parser's text |
| newer format | `version` above 1 | "Written in a newer format (2) than this Khipu reads (1). Update Khipu to see it." |
| wrong project | `project.id` differs from the registered project | "This file says it is for harbor, not atlas." Nothing from it is shown |
| refused | under a private folder | "Not read: the file is inside a private folder." |
| off | turned off in Settings | "Turned off" |
| none | the project has a ledger but no summary file | the board shows the ledger parts and "No job runner reports for this project" |

The last good read of each source is kept in Khipu's own state (`state/work/last/<project>.json`, cleaned
fields only) and replaced only by a newer good read.

### Waiting on you

One list across every project, built from three sources:

| Source | Shown as | Actions (all in the app) |
|---|---|---|
| A ledger row in state needs-owner | its title, project, kind, how long since it entered the state, its evidence and link | Done, Drop, Answered…, Open in the ledger, Open link |
| A Khipu commitment marked "needs the user" | its text, project, kind, age | Done (closes it), Snooze (a day, a week), Open in Owed |
| A pending or seeded routing rule; an owner hold at its reminder | "Confirm a standing rule a conversation changed", "6 seeded rules to confirm", "Your hold on Muse has been on for 90 days" | Open Routing settings |

**No duplicates.** A ledger row and a commitment are one item when they are linked: a ledger row may carry
`refs.commitment`, set by its writer or by Matt's "These are the same" (below). A linked pair shows once, as
the ledger row with "Also in Owed"; Done on it closes both, each with its own history. Khipu also links them
by itself when the project matches and the normalized text matches exactly (the commitments `content_hash`
rule). Anything less certain is never merged silently: when a commitment and a ledger row in the same
project look alike, the commitment shows "Looks like <ledger row title>" with These are the same and Not the
same, and either answer is remembered. Routing items never duplicate the others (they come from one place).

Order: blocking first (a Needs you ledger row that open rows sit under as their parent, and commitments of
kind blocker), then by how long each has waited, oldest first. Filters: All, Blocking, and
one chip per project. The first 8 show; "Show all 23" opens the rest in place. **Hide until it changes** is
Khipu's own record (`state/work/hidden.json`) for commitments only; ledger rows are closed, not hidden, and
routing items leave when confirmed. Settings lists hidden items with Unhide.

### The read model

`khipu work --json` builds one document, `khipu-work-view` version 1, kept at `state/work/view.json`
(replaced atomically). The desktop renders it, and a later phone or web view needs only it and the ledger
reads:

- `generated_at`, `valid_until` (the next moment the clock alone changes something).
- `projects[]`: `project`, `name`, `source` (`state`, `as_of`, `problem` as a fixed phrase, `dropped` and
  `capped` counts), `jobs[]`, `prs[]` (each with any ledger rows that name it and a `disagrees` phrase),
  `trains[]`, `merged[]`, `ledger` (counts by state; open goals with their children's counts; loose ends
  newest-changed first, at most 10; rows changed in the last 24 hours).
- `live[]`: every running, queued or waiting job across projects, with `account_ref` (routing's opaque
  account id and label when the job's account or lane matches, through `routing_lane_map`; otherwise the
  label as given and `matched: false`).
- `waiting[]`: the merged list above, each with its source, ids and actions.
- `accounts[]`: the routing projection the Home card uses, with each account's tightest Plans figure.
- `counts`: waiting (and blocking), running, flagged, stale sources, ledger outbox.
- Removed rows are in none of the above; the Removed list is read with `khipu ledger removed --json`.

A project's whole ledger is read page by page with `khipu ledger list --json` (the same order as render), not
carried in the view. Times are ISO 8601 UTC; every client words them locally. No paths, login folders,
account keys or raw file text appear, and no removed row. Khipu re-parses only summary files whose time or size changed; no
daemon is needed in this scope; the app asks every `work_refresh` while the Work tab is open, and once a
minute for the rail badge otherwise.

## Doctor

A `work` block: each summary source's state, last good read, dropped and capped counts, clamped times; a
`ledger` block: rows and history per project, outbox depth, whether the ledger tables are in the offline copy
and the dump, imports and whether any old tracker changed since, removed rows waiting to purge and purged markers. The outbox is red, as the capture outbox is;
everything else warns and never gates `ok`.

## What this will not do

- Act for a project. No approve, merge, retry, cancel or "move this job" control, here or later in this scope.
- Decide a ledger state. Khipu never marks work verified, done or dropped on its own, never removes a row on
  its own, and never infers a state from a pull request or a runner.
- Know more than writers say. A project with no runner shows its ledger and nothing live. Khipu does not read a
  project's git history, its pull requests on GitHub or its session transcripts to fill gaps.
- Tell a project's private data from a title. Rule 4 is the writers' contract; Khipu's checks limit the damage
  and do not make a careless writer safe.
- Reach a phone or the web. That needs the read model through the hub's gateway, its own scope and Matt's go.

## Decisions

1. The ledger lives in the hub database, with history, the outbox, the offline copy and the dump; never a
   state file.
2. Ledger rows are never reordered; every change keeps the old value and who made it. DROPPED keeps a row.
   Remove is the one way a row leaves: any writer may remove, it is gone everywhere at once, restorable in the
   app for 30 days, then purged to a bare marker so it never comes back; Matt can purge at once. Never
   automatic. (Matt, 2026-10-15: "If it can't be removable, that's a big problem.")
3. The CLI keeps the tracker's verbs, flags and printed shapes, so switching is one call; the MCP tool has the
   same verbs.
4. Import loses nothing, is verified by counts and a round trip, and rolls back otherwise; old files are kept
   and watched, never written.
5. PR stages and trains come from runner summaries; the ledger holds the durable claims and may name a PR or
   train; disagreements are shown, never resolved by Khipu.
6. The summary file has no waiting list; a need is a ledger row, so Matt can close it in the app.
7. Waiting on you merges ledger needs, commitments needing the user and routing items; exact matches and
   explicit links show once; near matches are only suggested.
8. One read model with no desktop-only data, so a phone or web view needs only a copy, not a redesign.
9. Every cap and time is a setting with Change… and, where it makes sense, No limit.
10. Accounts reuse the routing record and the Home card's rows; there is no second account list.
11. Each job shows one status line, the runner's own gist of what it is doing, about 90 characters, cleaned by
    Khipu; opening it shows up to the last 3. Never a feed of narration. (Matt, 2026-10-15.)
12. Work is a new tab after Home; Home stays. (Matt, 2026-10-15.)
13. Every active ledger switches together in phase 6, not one project at a time. (Matt, 2026-10-15.)
14. The Owed tab folds into Work as its own section ("Owed"), and the sidebar loses the separate tab. The
    Owed engine stays as it is: it still catches promises, blockers and questions from every conversation,
    including projects with no ledger, and still feeds the session-start push. (Matt approved the
    orchestrator's recommendation, 2026-10-15.) Phase 4 builds the section; the old Owed route opens it.

## Compatibility the import and the verbs must keep

An orchestrator that adopts the ledger first asked for these; they bind phases 1, 2 and 6.

1. Ids exactly as stored, including mixed forms (a bare PR number, a slug with letters and dashes).
   Lanes files and hand-off notes refer to rows by id.
2. Parent links exactly as written, including a parent that names a row which is absent. Such a row is
   shown under "parent not found", never re-parented or dropped.
3. The state vocabulary exactly, spaces included: VERIFIED, MERGED-UNVERIFIED, BUILT-UNMERGED, IN FLIGHT,
   QUEUED, NOT STARTED, NEEDS MATT, DROPPED, DONE. `add` and `set` refuse any other state the same way the
   tracker does (same exit code, a plain message naming the allowed words).
4. `render` writes the same markdown board as the tracker (same sections, same ordering), so a project
   that copies the board into its repo keeps working unchanged; `--out FILE` replaces the tracker's fixed
   output file.
5. History order and timestamps as stored (UTC strings ending in Z), including entries whose `from` is
   null (the row's creation).
6. The switch has an exact moment: the orchestrator stops writing its tracker file, the import runs and
   reports counts, and only then does the orchestrator start calling `khipu ledger`. Phase 6 messages each
   orchestrator with that moment before the import.
7. Each project keeps its own state and kind vocabulary. The three ledgers found on 2026-10-15 differ: one
   adds ON HOLD and the kinds audit-item, wave, train and drive; one uses the states complete and review with
   the kinds implementation and verification. The import records each project's vocabulary as found;
   `add` and `set` then refuse words outside that project's list. Khipu maps every word to one of four
   meanings it needs for the board and Waiting on you (open, done, dropped, needs you), and the mapping is
   shown in Settings → Work and changeable there. A word is never rewritten in the row itself.
8. Titles, notes and history text may span several lines (one note holds a full device listing). The import
   reads the JSON, never `list` output, and stores text as written.
9. History entries come in two shapes: {from, to, note, ts} and {at, event}. Both are kept verbatim; event
   text that records a user authorization is provenance and is never shortened.
10. Evidence paths are kept as recorded even when the file no longer exists; the row shows them as missing.
    The count check counts every recorded path.
11. Only the live file of each project is imported. Older copies and dated backups of the same ledger are
    checked to hold no row the live file lacks (by id), then left alone. Files beside a ledger that hold
    other work state (backlogs, follow-up lists, verification notes) are looked at in phase 6 before being
    ruled in or out.
